# 알라딘 만화 데이터 분석 대시보드 프로젝트 보고서

## 1. 문서 개요

| 항목 | 내용 |

## 2. 프로젝트 배경과 목표

### 2.1 배경

알라딘 만화 베스트셀러 페이지에는 도서별 순위, 제목, 작가, 출판사, 발매일, 가격, 평점, 판매지수 등 시장 흐름을 파악할 수 있는 정보가 HTML 형태로 제공된다. 그러나 웹페이지를 한 번 보는 것만으로는 다음과 같은 질문에 답하기 어렵다.

- 오늘 어떤 만화가 상위권에 올랐는가?
- 어제보다 순위가 상승하거나 하락한 도서는 무엇인가?
- 특정 시리즈의 여러 권이 동시에 순위에 들어왔는가?
- 특정 날짜의 순위, 평점, 판매지수를 다시 검색할 수 있는가?
- 내가 보유한 시리즈에서 빠진 권수는 무엇인가?

이 프로젝트는 알라딘 HTML을 정기적으로 수집하고, 수집 시점별 상태를 저장한 뒤, Django 화면에서 검색·비교·개인 소장 관리를 할 수 있도록 구성했다.

### 2.2 핵심 목표

1. 알라딘 만화 베스트셀러 전체 페이지를 BeautifulSoup으로 수집한다.
2. 원본 HTML과 정제된 CSV를 날짜별로 보존해 재현성과 추적성을 확보한다.
3. 이전 수집 시점과 비교해 순위 변동, 신규 진입, 이탈을 계산한다.
4. 같은 시리즈에 속한 권수를 집계해 인기 시리즈 순위를 산출한다.
5. Gold 데이터를 MySQL에 적재하고 Django가 이를 조회하게 한다.
6. 사용자가 검색, 정렬, 보유 권수 체크, 관심상품 관리, 폴더 정리까지 할 수 있게 한다.
7. Windows 작업 스케줄러로 매일 수집 파이프라인을 실행한다.

## 4. HTML 크롤링 설계

### 4.1 수집 대상

크롤러의 기본 URL은 알라딘 만화 베스트셀러 카테고리다. 첫 페이지는 기준 URL을 그대로 요청하고, 두 번째 페이지부터는 페이지 번호와 정렬 파라미터를 붙여 다음 페이지를 요청한다.

```python
https://www.aladin.co.kr/shop/common/wbest.aspx?BestType=Bestseller&BranchType=1&CID=2551
```

현재 크롤러는 페이지에 상품 링크가 더 이상 없거나, 해당 페이지에서 정상적으로 파싱된 도서가 없으면 종료한다. 상품 URL의 `ItemId`를 식별자로 사용하며, 페이지 간 중복 상품은 제거한다.

### 4.2 사용한 HTML 요소

| 추출 항목 | 주요 기준 |
|---|---|
| 상품 ID | 상품 링크의 `ItemId` 쿼리 값 |
| 제목 | `a.bo3` 링크 텍스트 |
| 도서 블록 | 상위 `div.ss_book_list` |
| 특전 문구 | 제목 옆 `span.ss_f_g2` |
| 평점 | `.star_score` |
| 판매지수 | `.sales_point` |
| 순위 | 상품 행의 첫 번째 직접 `td` |
| 작가·출판사·발매일 | 도서 정보 `li` 안의 텍스트·링크 |
| 가격 | 가격 영역의 `.ss_p2 em` 우선 사용 |

HTML 구조가 변경되면 선택자가 맞지 않아 상품 수가 줄거나, 필수 정보가 누락될 수 있다. 따라서 날짜별 원본 HTML을 함께 저장해 문제가 발생한 날의 화면 구조를 다시 확인할 수 있게 했다.

### 4.3 수집 필드

현재 Silver CSV의 기본 컬럼은 다음과 같다.

| 컬럼 | 의미 | 처리 방식 |
|---|---|---|
| `item_id` | 알라딘 상품 식별자 | 상품 URL의 `ItemId` |
| `title` | 원본 도서 제목 | 제목 텍스트 정리 |
| `series_name` | 시리즈명 | 제목에서 권수·판본을 보수적으로 분리 |
| `vol_no` | 권수 또는 권수 범위 | 숫자, `1~3` 등을 보존 |
| `edition_type` | 판본 유형 | 괄호 안 특장판·한정판·초판 등의 표현 |
| `special_benefits` | 제목 옆 특전 | `ss_f_g2` 문구를 그대로 정리 |
| `author` | 지은이 | `(지은이)` 역할이 붙은 사람만 추출 |
| `publisher` | 출판사 | 출판사 링크 또는 정보 텍스트 |
| `release_date` | 발매일 | 목록 페이지 기준 연·월 중심, 예: `2026-08` |
| `price` | 표시 가격 | 할인 가격이 있으면 할인 가격 우선 |
| `rating` | 평점 | 숫자로 변환 |
| `sales_point` | 판매지수 | 숫자로 변환 |
| `rank` | 베스트셀러 순위 | 행의 순위 셀, 실패 시 페이지 위치 보조 |
| `collected_at` | 수집 시각 | KST 기준 ISO 형식 |

### 4.4 제목 분리 정책

제목을 그대로 보존하는 `title` 컬럼은 유지하면서, 분석과 정규화를 위해 다음 항목을 별도로 만들었다.

- `series_name`: 작품 또는 시리즈의 기준 이름
- `vol_no`: `15`, `1~3`처럼 권수를 나타내는 부분
- `edition_type`: `(특장판)`, `(한정판)`, `(초판)`처럼 판본을 나타내는 괄호 내용

예를 들어 `주술회전 15 (특장판)`은 다음처럼 저장될 수 있다.

```text
title        = 주술회전 15 (특장판)
series_name  = 주술회전
vol_no       = 15
edition_type = 특장판
```

이 분리는 데이터베이스 정규화에 유리하지만, 동일 작품의 가이드북·모듈로·공식 팬북처럼 알라딘 제목이 다르게 표기되는 항목을 자동으로 같은 시리즈로 합치지는 않는다. 현재는 잘못 합치는 것보다 원래 구분을 보존하는 방향을 선택했다.

### 4.5 작가 추출 정책

정보 줄에 여러 역할이 함께 존재할 수 있기 때문에, 모든 링크를 작가로 저장하지 않는다. 링크 뒤에 `(지은이)`가 붙은 경우만 `author`에 넣고, 출판사 검색 링크는 제외한다. 이에 따라 글·그림·옮긴이 등 다른 역할은 현재 작가 컬럼에 들어가지 않는다.

### 4.6 발매일 정책

베스트셀러 목록 HTML에서 발매일이 대체로 `2026년 8월`처럼 월까지만 제공되므로, 현재 화면 정책은 월까지만 표시하는 것이다.

```text
원천 데이터: 2026-08
화면 표시: 2026.08
```

`dashboard/service/formatting.py`가 데이터 형식을 `YYYY.MM`으로 통일한다. 상세 페이지에서 일자를 추가로 확인하는 `release_date_enricher.py`는 존재하지만, 현재 요구사항에서는 사용하지 않는다.

## 5. Silver 데이터 설계

### 5.1 Raw와 Silver의 역할

이 프로젝트의 원천 데이터는 HTML 파일이다. HTML은 구조가 복잡하고 직접 분석하기 불편하므로, 크롤러가 요청한 필드를 CSV로 정리한다.

- `raw/YYYY-MM-DD/page_###.html`: 수집 당시의 원본 보존
- `aladin_manga.csv`: 가장 최근 실행의 전체 결과
- `history/aladin_manga_history.csv`: 모든 수집 시점의 누적 결과

`aladin_manga.csv`는 최신 실행 결과를 덮어쓰고, history CSV는 `item_id + KST 수집일`을 기준으로 관리한다. 같은 도서가 같은 날짜에 여러 번 수집되면 `collected_at`이 가장 최신인 행으로 교체하고, 실제 최신 수집 시각은 그대로 보존한다.

### 5.2 history를 보존하는 이유

현재 대시보드에 오늘의 데이터만 필요하더라도 history는 다음 분석에 필요하다.

- 전일 대비 순위 이동 계산
- 신규 진입 도서 확인
- 순위 이탈 도서 확인
- 특정 시리즈가 날짜별로 몇 권 노출됐는지 확인
- 수집 실패나 HTML 파싱 오류 발생 시 과거 결과 비교

원본 HTML과 정제 CSV를 함께 보관하면 “HTML에 실제로 무엇이 있었는가”와 “그 HTML을 코드가 어떻게 해석했는가”를 분리해 검증할 수 있다.

### 5.3 현재 Silver 단계의 의미

이 프로젝트의 Silver는 일반적인 데이터 플랫폼의 모든 표준을 구현한 계층이라기보다, HTML에서 필요한 컬럼을 추출하고 기본적인 값 정리·식별자 부여·날짜별 누적을 수행하는 운영 계층이다. 가격·평점·판매지수의 타입 변환과 제목 분리는 Gold 변환 전 단계에서 이미 이루어진다.

### 5.4 날짜별 중복 방지 정책

일일 수집은 원칙적으로 하루 한 번이지만, 네트워크 재시도·수동 테스트·작업 스케줄러 재실행으로 같은 날 여러 관측이 들어올 수 있다. 이를 다음 세 계층에서 방어한다.

1. `daily_snapshot.py`가 KST 날짜와 식별자를 조합해 최신 `collected_at` 행만 선택한다.
2. 크롤러의 `append_history()`가 history CSV를 날짜별 최신 행으로 다시 쓴다.
3. Gold 변환기와 적재기도 같은 기준으로 한 번 더 중복을 제거한다.

기존 이력을 일회성으로 정리할 때는 `normalize_history.py`를 사용한다. 원본 HTML은 실행일·페이지별로 보존하므로, CSV 정리 이후에도 당시 응답을 재확인할 수 있다.

## 6. Gold 변환 및 분석 로직

### 6.1 도서 추이 Gold

`gold_transform.py`는 history CSV에서 같은 도서·같은 KST 날짜의 최신 행만 선택한 뒤, 날짜별 최신 수집 시점을 직전 시점과 비교한다. 따라서 같은 날 재실행된 중간 관측은 Gold 비교 대상에서 제외된다.

Gold에 추가되는 파생 컬럼은 다음과 같다.

| 컬럼 | 의미 |
|---|---|
| `previous_rank` | 직전 수집 시점의 순위 |
| `rank_change` | 순위 변동 값 |
| `previous_sales_point` | 직전 판매지수 |
| `sales_point_change` | 판매지수 변동 값 |
| `is_new` | 직전 시점에 없었던 신규 관측 여부 |
| `is_out` | 현재 시점에 없어 이탈로 감지된 이벤트 여부 |

첫 수집분은 비교할 직전 데이터가 없으므로 기준선으로 처리한다. 이전 시점에는 있었지만 현재 시점에 없는 도서는 이탈 이벤트로 별도 행을 생성한다. 이 행은 마지막으로 확인된 도서 정보를 기반으로 만들고 `is_out=1`로 표시한다.

### 6.2 순위 변화 표시

대시보드 서비스는 Gold 값에 따라 화면용 상태를 붙인다.

| 상태 | 조건 | 화면 표시 |
|---|---|---|
| `new` | `is_new`가 참 | NEW |
| `baseline` | 비교값 없음 | BASE |
| `up` | 순위 변화가 양수 | 상승 화살표 |
| `down` | 순위 변화가 음수 | 하락 화살표 |
| `same` | 순위 변화가 0 | 대시 |

순위 숫자의 증감 부호가 사용자에게 직관적으로 보이도록 화면에서는 상승·하락 상태와 화살표를 함께 표시한다.

### 6.3 인기 시리즈 집계

시리즈 집계는 `series_name`과 수집일을 기준으로 오늘의 순위권 전체 도서를 그룹화한다. 같은 시리즈가 같은 날 여러 번 집계되면 최신 시각의 집계만 남는다. 이탈 행은 현재 순위표에 없는 도서이므로 집계에서 제외한다.

계산 항목은 다음과 같다.

- `volume_count`: 오늘 순위권에 등장한 도서 수
- `volume_numbers`: 등장한 권수 목록
- `best_rank`: 시리즈에 속한 도서 중 가장 높은 순위
- `avg_rank`: 시리즈 도서들의 평균 순위
- `total_sales_point`: 시리즈 도서 판매지수 합계
- `avg_sales_point`: 시리즈 도서 평균 판매지수

정렬 우선순위는 `volume_count` 내림차순, `total_sales_point` 내림차순, `best_rank` 오름차순, 시리즈명 순이다. 따라서 단순히 한 권의 판매지수만 높은 시리즈보다 오늘 여러 권이 동시에 순위에 등장한 시리즈가 우선된다.

### 6.4 Gold CSV

도서 추이 결과는 `gold/manga_trend.csv`, 시리즈 집계 결과는 `gold/popular_series.csv`에 저장한다. Gold CSV는 분석 결과를 확인하거나 재적재할 수 있는 중간 산출물이며, Django는 최종적으로 MySQL을 조회한다.

## 7. MySQL 데이터 모델

### 7.1 설계 방향

책의 변하지 않는 기본 정보와 날짜별로 변하는 순위 정보를 분리했다.

```text
series 1 ─── N books 1 ─── N book_snapshots
   │
   ├── N series_daily_stats
   └── 1 owned_series ─── N owned_series_volumes
```

Django 모델에는 `managed = False`를 사용한다. 즉 Django migration이 테이블을 만들거나 변경하지 않고, `mysql_schema.sql`과 `mysql_loader.py`가 스키마와 적재를 책임진다.

### 7.2 주요 테이블

| 테이블 | 역할 | 주요 키 |
|---|---|---|
| `series` | 시리즈 기준 정보 | `series_id`, `series_name` unique |
| `books` | 도서의 기본 정보 | `item_id` |
| `book_snapshots` | 수집일별 최신 순위·가격·평점·판매지수 | `item_id + collected_date` |
| `series_daily_stats` | 시리즈별 일일 집계 | `series_id + collected_date` |
| `owned_series` | 사용자가 보유 또는 관심으로 등록한 시리즈 | `owned_series_id`, `series_id` unique |
| `owned_series_volumes` | 실제 보유 체크 권수 | `owned_series_id + volume_no` |
| `owned_folders` | 보유 시리즈 폴더 | `folder_id` |
| `owned_series_folders` | 시리즈와 폴더 연결 | `owned_series_id` |
| `owned_series_positions` | 폴더 내부 시리즈 정렬 순서 | `owned_series_id` |

### 7.3 적재 방식

`mysql_loader.py`는 다음 방식으로 동작한다.

1. Gold CSV의 필수 컬럼을 검증한다.
2. `mysql_schema.sql`의 테이블을 확인·생성한다.
3. 기존 테이블에 `collected_date`가 없으면 날짜 생성 컬럼을 추가한다.
4. 기존 같은 날짜 중복 행을 찾아 오래된 행을 제거하고 날짜 기준 복합 기본키로 마이그레이션한다.
5. 시리즈명을 기준으로 `series`를 upsert한다.
6. 도서 기본 정보를 `books`에 upsert한다.
7. 도서·시리즈 일일 데이터를 날짜 기준으로 upsert한다.
8. 하나라도 실패하면 트랜잭션을 rollback한다.

`collected_at`은 최신 관측의 실제 시각을 보존하고, `collected_date`가 하루 단위의 유일성을 보장한다. 따라서 같은 날짜를 다시 적재하면 기존 행의 최신 시각과 지표가 갱신되며 새 행이 생기지 않는다.

## 8. Django 애플리케이션 구조

### 8.1 계층 분리

```text
Presentation
  └─ URL, request/response, redirect, 메시지
       ↓
Service
  └─ 화면용 계산, 상태 조합, 보유 권수·폴더 처리
       ↓
Repository
  └─ Django ORM 조회·저장, 외부 알라딘 조회
       ↓
MySQL
```

#### Presentation

`dashboard/presentation/urls.py`와 `views.py`가 담당한다.

- 페이지 URL 정의
- GET 검색 파라미터 수신
- POST 저장 요청 수신
- 성공·실패 메시지 처리
- 목록 페이지와 대시보드 템플릿 렌더링
- 폴더 및 시리즈 드래그 앤 드롭용 JSON 요청 처리

#### Service

`dashboard/service/`는 여러 Repository 결과를 조합해 화면에 필요한 값으로 만든다.

- `dashboard_service.py`: 최신 스냅샷, 전일 비교, 메인 50개, 인기 시리즈
- `search_service.py`: 검색 결과 페이지네이션, 최신 권수, 보유·관심 상태
- `owned_series_service.py`: 보유·관심 분리, 권수 체크, 진행률, 누락 권수, 폴더 이동
- `formatting.py`: 발매일을 `YYYY.MM`으로 표시

#### Repository

`dashboard/repository/`는 데이터 접근을 담당한다.

- `book_repository.py`: 스냅샷 시각, 도서 검색, 정렬
- `series_repository.py`: 시리즈별 오늘 집계
- `owned_series_repository.py`: 보유 시리즈, 보유 권수, 폴더, 정렬 순서
- `aladin_repository.py`: 알라딘 검색·상품·시리즈 페이지 조회

### 8.2 메인 대시보드

메인 화면은 최신 `collected_at`을 기준으로 동작한다.

- 오늘의 인기 만화 최대 50개
- 순위 상승·하락·신규·기준선 상태
- 제목과 판본 정보
- 별 버튼: 보유 목록 추가
- 하트 버튼: 관심상품 추가
- 저자와 시리즈명
- 평점
- 발매 연·월
- 오늘 전체 순위권에서 많이 등장한 인기 시리즈 상위 목록

화면 폭이 좁아지면 표가 카드형으로 변환되는 반응형 스타일을 적용했다. 사용자가 요청한 대로 메인 표에서는 판매지수 컬럼을 제거하고 발매일을 마지막 컬럼으로 배치했다.

### 8.3 검색 대시보드

검색 화면은 선택한 수집 스냅샷을 기준으로 결과를 조회한다.

- 수집 스냅샷 선택
- 전체 컬럼 검색
- 도서 ID, 제목, 시리즈명, 권수, 판본, 특전, 저자, 출판사, 발매일 검색
- 가격, 평점, 판매지수, 순위 검색
- 순위·평점·판매지수 오름차순/내림차순 정렬
- 페이지당 기본 50개, 최대 100개
- 시리즈명 아래에 해당 시리즈의 최신 관측 권수 표시
- 검색 결과가 없을 때 0건과 안내 문구 표시

현재 검색 대상은 알라딘 전체 만화 카탈로그가 아니라, MySQL에 저장된 순위 스냅샷이다. `is_out=False` 조건 때문에 선택한 시점의 현재 순위권 데이터만 검색한다. 한 번도 베스트셀러 페이지에 등장하지 않은 도서는 현재 검색할 수 없다.

전체 컬럼 검색에서 도서 ID를 ForeignKey 자체에 `icontains`로 적용해 오류가 발생하던 문제는 실제 `books.item_id` 문자열 컬럼을 검색하도록 수정했다. 또한 빈 `Page` 객체가 템플릿에서 거짓으로 평가되어 결과 패널이 숨겨지던 문제를 수정해, 결과가 0건이어도 `검색 결과가 없습니다`를 표시한다.

### 8.4 관심상품

관심상품은 보유 권수와 분리해 표시한다.

- 관심 시리즈 검색 및 추가
- 현재 로컬 데이터에서 최신 권수 참고
- 알라딘 검색어·상품번호·ISBN·URL을 이용한 외부 시리즈 조회
- 관심상품을 보유 목록으로 이동

관심상품 화면에는 보유 권수 체크 UI를 넣지 않는다. 관심 단계에서는 소장 상태를 관리하지 않는다는 사용자 요구를 반영한 것이다.

### 8.5 마이페이지(보유목록)

마이페이지는 실제 보유 권수를 관리하는 화면이다.

- 시리즈 검색 후 보유 목록 추가
- 순위권에서 별 버튼으로 시리즈 추가
- 알라딘 외부 검색으로 순위 밖 시리즈 추가
- 로컬 데이터 또는 외부 조회로 최신 권수 확인
- 최신 권수만큼 권별 체크박스 생성
- 저장 시 실제 보유 권수, 수집률, 미보유 권수 계산
- 보유 권수가 0이면 관심상품 영역으로 이동
- 폴더 생성·이름 변경·삭제
- 폴더 간 시리즈 이동
- 폴더 내부 시리즈 순서 변경
- 드래그 앤 드롭 후 순서 저장

보유 시리즈는 `owned_series`, 실제 체크 권수는 `owned_series_volumes`, 폴더와 순서는 각각 별도 테이블로 저장해 화면 표시와 사용자 상태를 분리했다.

### 8.6 외부 알라딘 조회

`aladin_repository.py`는 순위권 밖 시리즈를 보완하기 위한 조회 기능을 제공한다.

- 검색어를 알라딘 통합검색으로 전송
- 상품번호 또는 상품 URL로 상품 상세 페이지 조회
- ISBN은 통합검색으로 처리
- 시리즈 링크에서 시리즈명 추출
- 시리즈 페이지에서 최신 권수 계산
- 외부 조회 실패 시 사용자 메시지 표시

이 기능은 현재 시리즈 추가에 사용된다. 아직 알라딘 전체 도서 카탈로그를 주기적으로 수집해 검색하는 기능은 구현하지 않았다.

## 9. 일일 자동 실행

### 9.1 배치 파일

`run_daily_pipeline.bat`은 자신의 위치인 프로젝트 루트를 기준으로 Python 경로와 로그 경로를 계산한다. 따라서 프로젝트를 다른 위치로 옮겨도 배치 파일 내부의 고정된 한글 경로에 의존하지 않는다. `mysql_loader.py`와 Django 설정은 같은 프로젝트 루트의 `.env`를 읽으므로 작업 스케줄러가 PowerShell 환경변수를 별도로 전달하지 않아도 된다.

실행 순서는 다음과 같다.

```text
aladin_manga_scraper.py
    ↓
gold_transform.py
    ↓
mysql_loader.py
```

Python에 `-u` 옵션을 사용해 페이지별 출력이 버퍼에 오래 남지 않게 했고, 각 단계의 시작·종료 메시지를 `logs/daily_pipeline.log`에 기록한다.

### 9.2 검증된 최근 실행

2026-09-07 성공 실행 로그 기준으로 다음 결과를 확인했다. 해당 실행은 08:54:46에 시작해 08:55:59에 완료됐다.

| 항목 | 결과 |
|---|---:|
| 원본 HTML 페이지 | 21페이지 |
| 최신 수집 결과 | 1,000개 상품 |
| Gold 도서 행 | 6,717개 |
| 시리즈 집계 행 | 3,095개 |
| MySQL `books` 적재 | 1,553개 |
| MySQL `book_snapshots` 적재 | 6,717개 |
| MySQL `series_daily_stats` 적재 | 3,095개 |
| 최종 상태 | `SUCCESS` |

2026-09-04 중복 정리 과정에서는 Silver history가 7,000행에서 5,000행으로 줄었고, 9월 4일은 10:34:33의 최신 관측만 남겼다. MySQL에서도 도서·시리즈 중복 그룹이 각각 0개임을 확인했다. 2026-09-07에는 history 6,000행, Gold 도서 6,717행, 시리즈 3,095행이 생성되었고 날짜별 중복 없이 적재됐다.

이후 09:00에 별도 실행이 시작됐으나 중간 중단되어 `SUCCESS`가 기록되지 않은 시도도 있었다. 따라서 자동 실행의 성공 여부는 작업 시작 기록이 아니라 로그 마지막의 `SUCCESS`와 각 단계의 완료 메시지로 판단한다.

### 9.3 운영상 주의점

- 작업 스케줄러는 배치 파일을 실행할 뿐, Django 개발 서버를 자동으로 시작하지 않는다.
- MySQL 서비스가 실행 중이어야 적재가 성공한다.
- 작업 스케줄러가 실행하는 계정에서 프로젝트 루트의 `.env`와 가상환경을 읽을 수 있어야 한다.
- `.env`에는 MySQL 비밀번호가 포함되므로 Git에 커밋하거나 외부에 공유하지 않는다.
- PC가 절전·종료 상태이면 예약 시각을 놓칠 수 있다.
- 알라딘 응답이 느리거나 접근이 제한되면 크롤러 첫 요청에서 오래 대기할 수 있다.
- `CRAWL START` 이후 페이지 로그가 없으면 아직 Gold나 MySQL 단계가 아니다.
- 원본 HTML이 날짜 폴더에 생성되지 않으면 첫 HTTP 요청 또는 작업 권한·네트워크를 확인해야 한다.

### 9.4 다른 환경으로 이관

GitHub에는 소스 코드와 실행 문서를 올리고, `.env`·가상환경·원본 HTML·로그·MySQL 백업은 별도로 관리한다. 다른 컴퓨터에서는 저장소를 clone한 뒤 해당 컴퓨터의 경로에 맞춰 가상환경과 `.env`를 다시 만들고, 기존 순위·보유목록을 이어가려면 MySQL 백업과 history CSV를 복원한다.

`run_daily_pipeline.bat`은 자신의 위치를 기준으로 동작하므로 프로젝트 경로가 달라도 파일 자체를 수정할 필요가 없다. 반면 작업 스케줄러 등록 정보는 GitHub에 포함되지 않으므로 새 컴퓨터에서 다시 등록해야 한다. Django의 `127.0.0.1:8000`은 서버를 실행한 컴퓨터에서만 사용하는 주소이며, 다른 기기에서 접근할 때는 `0.0.0.0:8000`과 해당 컴퓨터의 내부 IP를 사용한다.

## 10. 현재 한계

### 10.1 데이터 범위

현재 크롤러가 수집하는 범위는 알라딘 만화 베스트셀러 페이지다. 따라서 MySQL의 `books` 전체는 알라딘 만화 전체 카탈로그가 아니라, 지금까지 순위권에 등장했거나 외부 추가 기능으로 등록된 도서에 가깝다.

순위에 한 번도 진입하지 않은 책을 모두 검색하려면 별도의 알라딘 검색·카탈로그 수집 파이프라인이 필요하다.

### 10.2 HTML 의존성

API가 아닌 HTML 선택자에 의존하므로 다음 변화에 영향을 받는다.

- CSS 클래스 변경
- 페이지 구조 변경
- 페이지네이션 파라미터 변경
- 봇 차단·응답 지연
- 빈 응답 또는 로그인·보안 페이지 반환

원본 HTML 보관은 이러한 변화의 원인을 추적하기 위한 장치지만, 자동 복구까지 제공하지는 않는다.

### 10.3 발매일 정밀도

목록 HTML이 월까지만 제공하므로 발매일은 `YYYY.MM` 수준이다. 일자까지 필요하면 상세 페이지를 추가 요청하는 보강 단계를 별도로 실행해야 하지만, 요청량 증가와 사이트 접근 부담을 고려해 현재 일일 파이프라인에는 포함하지 않았다.

### 10.4 사용자·보안

현재 Django 프로젝트는 개인용 로컬 대시보드에 맞춰져 있다.

- 사용자 인증·권한 분리 없음
- `DEBUG=True` 개발 설정
- 보유목록은 단일 사용자 기준
- MySQL 비밀번호는 프로젝트 루트 `.env`로 관리하며 코드·배치 파일에 넣지 않음
- 운영 서버 배포용 정적 파일·보안 설정은 별도 필요

## 11. 개선 계획

우선순위가 높은 개선 항목은 다음과 같다.

1. 크롤러에 재시도·지수 백오프·상태 코드별 메시지 추가
2. HTTP 연결 타임아웃과 읽기 타임아웃을 분리하고 실패 페이지를 명시적으로 기록
3. 작업 실행 이력 테이블 또는 별도 run manifest 추가
4. 작업 스케줄러 실패 시 알림 또는 간단한 상태 점검 기능 추가
5. 알라딘 HTML이 차단 페이지인지 판별하는 검증 로직 추가
6. 순위 밖 도서를 검색할 수 있는 별도 카탈로그 수집 기능 추가
7. `books`와 스냅샷을 분리한 전체 도서 검색 화면 설계
8. 현재 Django 모델에 맞는 테스트 데이터와 자동화 테스트 확장
9. 사용자 인증을 추가해 여러 사용자의 보유목록을 분리
10. 운영 배포 시 `DEBUG=False`, secret key·DB 비밀번호·ALLOWED_HOSTS 분리

순위 밖 검색은 현재 검색 기능을 실시간 알라딘 크롤러로 교체하기보다, 기존 MySQL 검색을 유지하면서 `알라딘에서 검색` 기능을 별도 추가하는 방향이 적합하다.

## 12. 결론

이 프로젝트는 단순 HTML 크롤러에서 출발해 다음 흐름을 갖춘 개인 데이터 애플리케이션으로 확장됐다.

```text
HTML 원본 보존
→ 정제된 날짜별 데이터
→ 전일 대비 Gold 분석
→ MySQL 데이터웨어하우스
→ Django 탐색·시각화
→ 개인 보유·관심 관리
```

현재 핵심 목표인 “매일 알라딘 만화 순위 수집, 추이 분석, 대시보드 출력”은 구현된 상태다. 다음 단계는 기능을 무작정 늘리기보다 크롤러 실패를 안정적으로 감지하고, 순위 밖 도서 범위를 어떻게 확보할지 결정하는 것이다.
